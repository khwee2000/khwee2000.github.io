평균 90.9점이면 믿어도 될까? 생성 글의 틀린 날짜를 따로 잡기까지

지하철 소식을 블로그 글로 자동 발행한다. 날짜 · 노선은 원문과 맞춘다.

  4. 2024.03–06 캡스톤 · 코드 공개

풀어야 했던 문제 생성 글에 원문에 없는 내용이 섞였고, 유사도 점수로는 사실이 틀린 글을 잡지 못했어요.

기간 · 인원 2024.03 – 06 · 4인 팀(팀장) · 협업사 지하철온다내 몫 4인 팀장 · 수집 · 정제 · 통합 파이프라인검증 단계 캡스톤 · 실제 블로그 발행코드 GitHub 레포 (새 탭)

템플릿 · 날짜 · 노선 · 품질 대조

85.8점템플릿

  • 그런데 평균 90.9점에도 날짜를 틀리는 글이 남아 있었어요.

3) 최종 파이프라인 (Final)

Reason

  • 점수가 높아도 틀리면 안 되는 칸은 원문과 따로 대조해야 했어요.
  • 싼 규칙 검사부터 돌리고, 비싼 검사는 뒤에 뒀어요.

4) 검증 (Test) — 점수 뒤에 남은 것

  • 날짜 · 노선은 원문과 대조
  • 템플릿 · 품질 검사

점수는 LLM 채점이에요. 사람이 읽고 매긴 점수가 아니라서, 틀리면 안 되는 사실은 점수와 따로 셌어요.

아직 확인 전 발행 뒤 독자가 찾은 오류는 따로 세 보지 않았어요.

자세한 이야기

안녕하세요. 공공 상담 · 복지 데이터로 모델을 만들고 평가 기준을 세워 온 김민수예요.

지하철 소식을 전하는 블로그 ‘지하철온다’는 뉴스를 바탕으로 글을 써 왔어요. 사람이 쓰면 글 한 건에 2만 원과 1시간이 들었어요. 그래서 4인 팀으로 이 과정을 생성형 AI로 자동화하는 캡스톤을 했는데요.

결론부터 말하면, 글 한 건이 약 500원 · 2분이 됐고 주 2회 자동으로 발행했어요. 그런데 이 글에서 하고 싶은 이야기는 그 숫자보다, 평균 90.9점 뒤에 남아 있던 틀린 날짜예요.

원문과 비슷하면 좋은 글일까요?

생성형 AI로 바꾸자 원문에 없는 내용이 섞이기 시작했어요. 처음에는 익숙한 유사도 점수(BLEU, 원문과 단어가 얼마나 겹치는지)로 쟀는데요, 같은 내용을 다른 문장으로 쓴 글은 낮게, 사실이 틀린 글은 오히려 높게 나올 수 있었어요.

무엇을 잴지부터 다시 정해야 했어요.

원문과 비슷한지가 아니라, 원문과 사실이 맞는지를요.

사실 일치를 따로 재기

팀은 평가 축을 다시 정하고, G-Eval 기반 평가로 바꿨어요. 그리고 생성을 기사 이해 · 항목별 작성 · 원문 대조 세 단계로 나눴어요.

  • 내용 완성도 — 기사의 핵심이 빠짐없이 들어갔는지
  • 가독성 — 블로그 글로 읽히는지
  • 사실 일치도 — 원문과 사실이 맞는지. 가장 큰 가중치를 뒀어요.

평균 90.9점에도 남은 것

점수는 65.8점에서 90.9점으로 올랐어요. 그런데 평균이 90.9점인데도 날짜를 틀리는 글이 남아 있었어요. 지하철 소식에서 날짜와 노선은 틀리면 안 되는 칸이에요. 평균 점수가 높다고 그 글을 믿을 수는 없었어요.

그래서 평균과 개별 사실을 다른 문제로 봤어요. 날짜 · 노선 같은 핵심 정보를 원문과 따로 대조하는 단계를 포함해 3단계 검증을 붙였어요.

싼 검사부터 돌리기

검사를 셋 다 매번 돌리면 비용이 커져요. 그래서 싼 검사부터 돌리고, 앞에서 걸리면 뒤 검사는 건너뛰었어요.

순서검사한 번에 드는 값
1템플릿 준수13.64원
2핵심 정보(날짜 · 노선) 대조22.87원
3전체 품질 평가48.02원

세 검사를 다 거쳐도 건당 84원이었어요. 사람이 쓰던 2만 원과 비교하면, 검증까지 붙이고도 비용이 크게 줄어든 셈이에요.

제가 맡은 것: 수집 · 정제 · 통합

평가 설계와 3단계 검증은 팀의 작업이에요. 저는 4인 팀의 팀장으로, 뉴스를 모으고 정제해 생성 단계로 넘기는 데이터 파이프라인(Newspaper3k · Selenium · SpaCy)을 맡았어요. 생성과 검증이 아무리 좋아도, 들어가는 원문이 깨져 있으면 사실 대조도 할 수 없거든요.

고려했지만 선택하지 않은 것

  • 유사도 점수를 올리기 — 익숙한 지표지만, 사실이 틀린 글도 점수가 높을 수 있었어요.
  • 모든 글에 검사 셋을 다 돌리기 — 정확하지만 비싸서, 싼 검사부터 돌리고 걸리면 멈추는 순서로 바꿨어요.

SK브로드밴드에서라면

AT R&D가 공개한 일 가운데 이 문제와 같은 모양의 일이 있어요. 가입 예측 + SHAP + LLM 상담 멘트(KICS 2025)13이에요.

  • 공개된 내용 — SHAP 상위 요인을 LLM에 넣어 고객별 멘트를 만든다. 논문은 생성 멘트의 품질 · 설득력 검증을 '향후 연구'로 남겼다(SKB 저자 논문 — 팀 소속은 확인하지 못했다).
  • 같은 점 — 예측 · 설명 · 사람이 읽는 문장으로 이어지는 구조
  • 같은 점 — 생성 문장이 근거와 맞는지가 마지막 관문
  • 해 보지 않은 것 — SHAP 결과를 LLM 문장으로 바꿔 본 적은 없다 — 이어 본 것은 블잇의 생성문 검증

그래서 입사하면 먼저 가져가고 싶은 건 이거예요.

멘트 속 주장을 다시 뽑아 입력 요인과 대조하는 '주장–근거 일치율'

마치며

이 일에서 알고 싶었던 건 ‘평균이 몇 점인가’가 아니라 ‘틀리면 안 되는 칸이 맞는가’였어요.

배운 점 및 피드백

  1. 무엇을 잴지부터 정했는가?

    팀은 유사도 대신 사실 일치에 가장 큰 가중치를 두는 평가로 바꿨어요.

    입사하면생성 결과는 원문과 비슷한지가 아니라 사실이 맞는지로 잴게요.

  2. 평균과 개별 사실을 구분했는가?

    평균 90.9점 뒤에 남은 틀린 날짜를 따로 대조하는 검증을 붙였어요.

    입사하면AI 상담 답변도 틀리면 안 되는 칸(요금 · 날짜 · 상품명)을 따로 검사할게요.

  3. 검증 비용까지 설계했는가?

    싼 검사부터 돌리고 걸리면 멈추는 순서로 건당 84원에 맞췄어요.

    입사하면검증 단계도 비용 순서로 쌓아 운영할 수 있게 만들게요.

팀은 이 프로젝트로 캡스톤디자인 결과발표회에서 총장특별상을 받았어요. 코드는 GitHub에, 발행된 글은 지하철온다 블로그에 있어요. 읽어 주셔서 감사해요.
