03 과정

자세한 이야기

안녕하세요. 공공 상담 · 복지 데이터로 모델을 만들고 평가 기준을 세워 온 김민수예요.

이번 과제의 질문은 단순했어요. “상담 음성을 AI로 활용할 수 있는가.” 그런데 한국어 상담 음성에는 잡음과 겹말이 많고, 제도 용어가 계속 나와요. 범용 음성인식 모델의 성능이 그대로 재현되지 않았어요. 개인정보가 담겨 있어 외부 API도 쓸 수 없었고요.

결론부터 말하면, 이 일은 성능을 올리는 일이 아니라 어떤 조건에서 쓸 수 있고 어디서 무너지는지를 답하는 일이었어요. 그래서 모델보다 성공 기준과 장비 사양을 먼저 정했어요. 과제는 아직 진행 중이라, 이 글에는 지금까지 확인한 것만 적었어요.

성능을 올리는 일과 증명하는 일은 같을까요?

보통 이런 과제는 모델을 고르고 성능을 끌어올리는 데서 시작해요. 그런데 ‘쓸 수 있는가’에 답하려면, 먼저 ‘무엇을 맞는 결과로 볼 것인가’가 정해져 있어야 해요.

정답 데이터의 기준이 없으면, 어떤 지표도 의미가 없어요.

오류율이 몇 퍼센트라고 말해도, 무엇을 정답으로 놓고 잰 숫자인지 합의되지 않았다면 아무도 그 숫자를 믿고 쓸 수 없거든요.

계약 전에 안 되는 것부터 꺼냈어요

이 규모의 장비 설계는 저도 처음이었어요. 그래서 착수 조건부터 짚었어요. 계약을 빨리 맺는 데는 도움이 안 되는 이야기였지만, 착수 뒤에 드러났다면 되돌릴 수 없었을 위험이었어요.

  • 정답 데이터 기준 — 무엇을 맞는 전사로 볼지, 그 정답을 어떻게 확보할지
  • 오류율 목표 — 요구된 목표 수치가 현실적인지
  • 모델 사양 — 요구된 모델 사양이 실제 조건에 맞는지
  • 일정 — 정해진 기한 안에 처리할 수 있는지

장비 사양을 감이 아니라 측정으로

처리할 양을 기한으로 나눠 하루에 처리해야 할 양을 거꾸로 계산하고, 모델별로 GPU 메모리와 추론 속도를 직접 쟀어요.

하루 처리량 = 전체 음성 ÷ 기한(일)
# 모델별로 직접 잰 값: GPU 메모리 · 추론 속도
# 단일 구성의 처리 속도가 하루 처리량에 못 미치면 병렬로 구성

재 보니 단일 구성으로는 기한을 맞출 수 없다는 게 숫자로 확인됐어요. 그래서 병목을 비교한 뒤 병렬로 구성했고, 서버 구성별 속도와 비용을 비교해 사양을 정했어요.

인식을 키울까, 교정을 붙일까

오류를 뜯어보니 고르게 퍼져 있지 않았어요. 특정 제도 용어와 띄어쓰기에 몰려 있었어요. 여기서 두 길이 있었는데요, 인식 모델을 키워서 한 번에 다 잡는 것과, 인식 뒤에 소형 LLM 후처리를 붙여 회수하는 것이었어요.

비용 대비 효과는 후처리 쪽이 컸어요. 그래서 인식과 교정을 두 단계로 나눴고, 음성 인식부터 개인정보 탐지 · 비식별화까지 모든 구간이 폐쇄망 안에서 돌게 만들었어요.

평균 하나 대신 구간별로 평가하기

전체 평균 오류율은 쓰지 않기로 했어요. 대신 발화 길이와 용어 밀도로 구간을 나눠 평가해, 어디서 무너지는지를 드러내게 했어요. ‘쓸 수 있는가’에 대한 답은 평균 하나가 아니라 ‘이 조건에서는 쓸 수 있고, 저 조건에서는 아직 아니다’에 가깝다고 봤거든요.

지금까지 확인한 것

  • 하루 처리량 역산과 온프레미스 서버 사양 산정
  • 폐쇄망 안에서 음성 인식, 개인정보 탐지, 비식별화까지 잇는 파이프라인
  • 인식 + 후처리 두 단계로 용어 · 띄어쓰기 오류 회수 — 중간 측정에서 오류율 감소 확인
  • 발화 길이 · 용어 밀도별 구간 평가 기준

현장 검증은 아직 진행 중이에요. 그래서 현업이 실제로 쓴 기록은 아직 없어요.

  • 공개된 내용 — API 모델의 환각 · 오너십 · 토큰 비용 때문에 상담 매뉴얼을 정제해 sLLM을 직접 세웠다(PEFT + RAG).
